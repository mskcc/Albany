# Open Issues

## v_fastqs is too slow on DLP samples

Found 2026-11-15. `dumpLimsDB.py` hung after writing the third CSV, and
Ctrl-C did not stop it. As a workaround, `dumpLimsDB.py` no longer dumps
`v_fastqs` (commit f75bbd9). The view is still in the database, and any
query on it that reaches a DLP sample still hangs.

### Cause

DLP (single-cell whole-genome) samples store the whole chip as one IGO
sample, with one FASTQ file per cell, lane and read, all in one library
and one run:

| igo_id | JSON size | libraries | runs | FASTQ files |
|---|---|---|---|---|
| 11881_P_1 | 3.9 MB | 1 | 1 | 28,944 (4,824 cells x 3 lanes x 2 reads) |
| 06000_OZ_1 | 2.9 MB | 1 | 1 | 20,736 |
| 11881_Q_1 | 2.7 MB | 1 | 2 | 19,296 |

In total, 28 manifests have FASTQ paths in DLP run directories.

`v_fastqs` (`limsDB.py`, `VIEWS_SQL`) loops over library, then run,
then FASTQ file with nested `json_each`. The columns `libraryIgoId`,
`runId`, `flowCellId` and `runDate` are computed again for every FASTQ
row from `lib.value` and `run.value`. For these samples each of those
is the full multi-MB library text, which SQLite rebuilds and searches
for every row. `_json_column` also calls `json_extract` twice per
column (once in the `CASE WHEN` test, once in `THEN`). The work grows
with the square of the number of FASTQ files in a sample: about
29,000 rows x 8 calls x 3.9 MB for 11881_P_1 alone.

Ctrl-C does not work because the query runs inside one call into
SQLite's C code (`fetchall()`), and Python's `sqlite3` module does not
stop that call on SIGINT. Use Ctrl-\ or `kill -9`.

### Proposed fix

Rewrite `v_fastqs` so the library and run fields are computed once per
library and once per run, using `MATERIALIZED` CTEs:

1. For each library: `libraryIgoId` and its `runs` array.
2. For each run: `runId`, `flowCellId`, `runDate` and its `fastqs`
   array.
3. Expand the `fastqs` array into one row per file.

The work then grows only with the size of the data. Keep the view name
and columns, and bump `limsDB.SCHEMA_VERSION`. Check that the rows
match the old view on a small sample, and time it on 11881_P_1 alone,
before adding `v_fastqs` back to `dumpLimsDB.VIEWS`.

The other option is to build the FASTQ table in Python with
`json.loads` in `dumpLimsDB.py`. That is also linear, but leaves the
view slow for R and SQL users.
